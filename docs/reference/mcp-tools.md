# MCP tools

Every tool the `loom` server exposes over `php artisan loom:mcp`; names, descriptions and inputs are generated from the tool classes, so they are what a client sees. To register the server and see what to ask, read [Ask an agent](../guides/ask-an-agent.md).

All tools are read-only and return one JSON document as text. Tool, input and output key names are stable: renaming or removing one is a major change, adding an optional input or output key is minor.

## Conventions

- Class names are fully qualified and case-sensitive; JSON output escapes backslashes.
- `depth` counts handler-to-dispatch hops. Values outside `1` to `6` are clamped, not rejected, and the response echoes the depth used.
- `method_fqcn` is `Class::method`, `Class@method`, or a bare `Class` for every method it has.
- Output keys are snake_case. `handler_kind` is `listener` or `closure`, and a closure handler is named `file:line`.
- Errors are a text message instead of JSON. Empty results are not errors unless noted below.

Transitive closure starting from a Class::method (or Class@method, or a bare Class for every method): what it dispatches, then the event chain following each dispatched event. | Input | Type | Required | Default | Notes |

### `route-to-events`

Resolve an HTTP route (verb + URI) to the event chain its controller action triggers. Matches case-insensitively on verb and exactly on URI (leading slash optional), then follows the controller method through the dispatch graph (depth 1..6, default 3). Closure or unresolved-controller routes return an empty chain with a note.

| Input | Type | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `method` | string | yes | none | The HTTP verb, e.g. GET or POST (case-insensitive). |
| `uri` | string | yes | none | The route URI, e.g. orders or /orders (leading slash optional). |
| `depth` | integer | no | `3` | How many handler→dispatch hops to follow per chain (clamped to 1..6). |

### `impact-of-change`

Blast-radius report for removing or renaming a class. For an event: who dispatches it, who handles it (named + closure listeners), and the transitive downstream chain. For a listener/job: which events it handles and whether removing it would orphan an event (an event whose only handler is this class). Notes call out what static analysis cannot determine.

| Input | Type | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `fqcn` | string | yes | none | The fully-qualified class name being changed (event, listener, or job). |
| `change` | string | no | `"remove"` | The kind of change being made. Affects the framing of the notes only. One of `remove`, `rename`. |

### `find-orphans`

List dead-weight in the event graph: orphan events (dispatched from nowhere AND handled by nothing) and idle listeners (registered but handling no events). A review aid — dynamically dispatched or reflection-registered cases may not surface statically.

No inputs.

## Responses

| Tool | Response |
| --- | --- |
| `list-entities` | `{ section, count, items }`; `items` are that [index](schema.md) section verbatim. An unknown `section` is an error listing the valid ones. |
| `get-entity` | `{ kind, fqcn, found, entity }`; `entity` is the raw entry. A missing class returns `No job found for App\Nope.`; an unknown `kind` lists the valid kinds. |
| `dispatch-sites-for` | `{ event, count, dispatch_sites }`, each `{ file, line, method }`. An event nothing fires gives `count: 0`; an empty `event_fqcn` is an error. |
| `handlers-for` | `{ event, count, listeners, closure_listeners }`; `count` covers both. Closure listeners are identified by file and line. |
| `dispatches-from` | `{ method_fqcn, count, dispatches }`, each `{ target, kind, confidence, file, line }`. Only routes resolve to an exact method; a listener, observer or job answers for the whole class. |
| `events-following` | `{ root, depth, edges, events_reached, cycles, truncated }`. An edge is one handler of one event: `{ event, handler, handler_kind, dispatches }`. `truncated` is `true` when `depth` cut a chain short, `cycles` lists events revisited on a path, each event is expanded once, and a target missing from `events_reached` was left unexpanded. An unknown event gives empty `edges`. |
| `events-from-method` | `{ method_fqcn, dispatches, chains }`: `dispatches-from` plus one `events-following` result per dispatched event. An unknown method gives both empty. |
| `route-to-events` | `{ route, note, chain }`; `chain` is an `events-from-method` result and `note` is `null` when it resolved. A closure route gives `chain: null` and a note; no matching verb and URI is an error. |
| `impact-of-change` | For a listener: `{ fqcn, change, kind, handles, would_orphan_events, dispatches, notes }`. For an event: `dispatchers`, `handlers` (`{ handler, handler_kind }`) and a `downstream` chain. An unknown class gives `kind: "unknown"`, `downstream: null` and a note; an unrecognised `change` is an error. |
| `find-orphans` | `{ orphan_events, idle_listeners }`. An event fired only from an unresolved dispatch can look orphaned; cross-check with `find-unresolved-dispatches`. |
| `find-unresolved-dispatches` | `{ count, unresolved_dispatches }`, each `{ file, line, expression, reason }`. Reasons are explained in [Why was my code missed](../guides/why-was-my-code-missed.md#a-dispatch-shows-up-as-unresolved). |
