# MCP tools

Every tool the `loom` server exposes over `php artisan loom:mcp`, with its inputs, a real response and the errors it can return. To register the server and see what to ask, read [Ask an agent](../guides/ask-an-agent.md).

All tools are read-only and return one JSON document as text. Tool, input and output key names are stable: renaming or removing one is a major change, adding an optional input or output key is minor.

The input tables and every response below are generated, the responses by running the tools against a small order app: `POST /orders` runs `OrderController::store`, which fires `OrderPlaced`; `SendReceipt` handles it, fires `ReceiptSent` and queues `SendMail`; `ArchiveReceipt` and a closure listener handle `ReceiptSent`, and the closure fires `ReceiptLogged`. The app also has an `OrderCancelled` event nothing uses and an `AuditOrders` listener that handles no event.

## Conventions

- Class names are fully qualified and case-sensitive, written the way PHP writes them (`App\Events\OrderPlaced`). In JSON output the backslashes are escaped, so they appear as `App\\Events\\OrderPlaced`.
- `depth` counts handler-to-dispatch hops, default `3`. Values outside `1` to `6` are clamped, not rejected, and the response echoes the depth used.
- `method_fqcn` is `Class::method`, `Class@method`, or a bare `Class` for every method it has.
- A handler is `Class::method` for a listener and `file:line` for a closure; `handler_kind` is `listener` or `closure` accordingly.
- Errors come back as a text message instead of JSON. Empty results are not errors unless a tool says otherwise.

### Chain output

`events-following`, `events-from-method`, `route-to-events` and `impact-of-change` embed the same chain, which always carries:

- `truncated`: `true` when `depth` cut a chain short.
- `cycles`: events revisited on a path. Each event is expanded once, so a cycle does not repeat.
- `events_reached`: the events whose handlers were expanded. A `target` that is not in it was left unexpanded.

### `list-entities`

| Input | Type | Required / default | Notes |

## Edges

## Chains

Follow dispatches transitively, down to `depth` hops.

### `events-following`

Follows an event to its handlers, what they dispatch, and the handlers of those events, down to `depth` hops.

| Input | Type | Required / default | Notes |
| --- | --- | --- | --- |
| `event_fqcn` | string | required | The fully-qualified class name of the event to follow. |
| `depth` | integer | `3` | How many handler→dispatch hops to follow (clamped to 1..6). |

### `events-from-method`

Starts from a method: what it dispatches, then the chain that follows each dispatched event.

| Input | Type | Required / default | Notes |
| --- | --- | --- | --- |
| `method_fqcn` | string | required | The method to start from, e.g. App\Http\Controllers\OrderController::store. |
| `depth` | integer | `3` | How many handler→dispatch hops to follow per chain (clamped to 1..6). |

Called with `method_fqcn` = `App\Http\Controllers\OrderController::store`, `depth` = `1`, it returns:

```json

          "event": "App\\Events\\OrderPlaced",
          "handler": "App\\Listeners\\SendReceipt::handle",
          "handler_kind": "listener",
          "dispatches": [
            {
              "target": "App\\Events\\ReceiptSent",
              "kind": "event",
              "confidence": "high",
              "file": "app/Listeners/SendReceipt.php",
              "line": 13
            },
            {
              "target": "App\\Jobs\\SendMail",
              "kind": "job",
              "confidence": "high",
              "file": "app/Listeners/SendReceipt.php",
              "line": 14
            }
          ]
        }
      ],
      "events_reached": [
        "App\\Events\\OrderPlaced"
      ],
      "cycles": [],
      "truncated": true
    }
  ]

```

- `dispatches` is what `dispatches-from` returns; `chains` holds one `events-following` result per dispatched event.
- This call used `depth` `1`, so `truncated` is `true`: the chain stops before the handlers of `ReceiptSent`.
- An unknown method returns empty `dispatches` and `chains`.
- Method granularity is exact only for routes; a listener, observer or job resolves at class level.

### `route-to-events`

| `method` | string | required | The HTTP verb, e.g. GET or POST (case-insensitive). |
| `uri` | string | required | The route URI, e.g. orders or /orders (leading slash optional). |
| `depth` | integer | `3` | How many handler→dispatch hops to follow per chain (clamped to 1..6). |

Takes no input.

```json

    {
      "fqcn": "App\\Events\\OrderCancelled",

### `find-unresolved-dispatches`

Lists every dispatch Loom could not trace to a class, with the raw expression and a reason code.

Takes no input.

Called with no input, it returns:

  "unresolved_dispatches": [

```

- Each `reason` links to the code that produces it in [What Loom detects](detection/index.md#unresolved-reasons).
