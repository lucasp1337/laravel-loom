# MCP tools

Every tool the `loom` server exposes over `php artisan loom:mcp`. The tool names, descriptions and inputs below are generated from the tool classes, so they are what a client sees. For how to register the server and what to ask it, see [Ask an agent about your events](../guides/ask-an-agent.md).

All tools are read-only and return one JSON document as text. Tool names, input names and output key names are stable: renaming or removing one is a major change, adding an optional input or an output key is minor.

## Conventions

- Class names are fully qualified and case-sensitive (`App\Events\OrderPlaced`). In JSON output backslashes are escaped (`App\\Events\\OrderPlaced`).
- `depth` is a number of handler-to-dispatch hops. Values outside `1` to `6` are clamped, not rejected, and the response echoes the depth used.
- A method reference (`method_fqcn`) is `Class::method`, `Class@method`, or a bare `Class` for every method it has.
- Output keys are snake_case. Wherever a handler is described, `handler_kind` is `listener` or `closure`; a closure handler is named `file:line`.
- Errors come back as a text message instead of JSON. Empty results are not errors, except where noted below.

### `events-following`

| Input | Type | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `event_fqcn` | string | yes | none | The fully-qualified class name of the event to follow. |
| `depth` | integer | no | `3` | How many handler→dispatch hops to follow (clamped to 1..6). |

### `events-from-method`

Transitive closure starting from a Class::method (or Class@method, or a bare Class for every method): what it dispatches, then the event chain following each dispatched event. Depth bounds the chain (1..6, default 3). Method granularity is exact only for routes; listeners/observers/jobs resolve at class level.

| Input | Type | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `method_fqcn` | string | yes | none | The method to start from, e.g. App\Http\Controllers\OrderController::store. |
| `depth` | integer | no | `3` | How many handler→dispatch hops to follow per chain (clamped to 1..6). |

### `route-to-events`

Resolve an HTTP route (verb + URI) to the event chain its controller action triggers. Matches case-insensitively on verb and exactly on URI (leading slash optional), then follows the controller method through the dispatch graph (depth 1..6, default 3). Closure or unresolved-controller routes return an empty chain with a note.

| Input | Type | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `method` | string | yes | none | The HTTP verb, e.g. GET or POST (case-insensitive). |
| `uri` | string | yes | none | The route URI, e.g. orders or /orders (leading slash optional). |
| `depth` | integer | no | `3` | How many handler→dispatch hops to follow per chain (clamped to 1..6). |

### `impact-of-change`

Blast-radius report for removing or renaming a class. For an event: who dispatches it, who handles it (named + closure listeners), and the transitive downstream chain. For a listener/job: which events it handles and whether removing it would orphan an event (an event whose only handler is this class). Notes call out what static analysis cannot determine.

| Input | Type | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `fqcn` | string | yes | none | The fully-qualified class name being changed (event, listener, or job). |
| `change` | string | no | `"remove"` | The kind of change being made. Affects the framing of the notes only. One of `remove`, `rename`. |

### `find-orphans`

List dead-weight in the event graph: orphan events (dispatched from nowhere AND handled by nothing) and idle listeners (registered but handling no events). A review aid — dynamically dispatched or reflection-registered cases may not surface statically.

No inputs.

### `find-unresolved-dispatches`

List dispatch sites the scanner could not statically resolve to a target, with the raw expression, reason, file and line. Surfaces what static analysis could not pin down.

No inputs.

## Responses

| Tool | Response |
| --- | --- |
| `list-entities` | `{ section, count, items }`; `items` are the entries of that [index](schema.md) section verbatim. An unknown `section` is an error listing the valid ones. |
| `get-entity` | `{ kind, fqcn, found, entity }`; `entity` is the raw index entry. A missing class returns `No job found for App\Nope.` (with the kind asked for); an unknown `kind` lists the valid kinds. |
| `dispatch-sites-for` | `{ event, count, dispatch_sites }`; each site is `{ file, line, method }`. An event nothing fires returns `count: 0`. An empty `event_fqcn` is an error. |
| `handlers-for` | `{ event, count, listeners, closure_listeners }`; `count` is both lists together. Closure listeners are identified by file and line. |
| `dispatches-from` | `{ method_fqcn, count, dispatches }`; each is `{ target, kind, confidence, file, line }`. Only routes resolve to an exact method; for a listener, observer or job the answer covers the whole class. |
| `events-following` | `{ root, depth, edges, events_reached, cycles, truncated }`. Each edge is one handler of one event: `{ event, handler, handler_kind, dispatches }`. `truncated` is `true` when `depth` cut a chain short, `cycles` lists events revisited on a path, and each event is expanded once. `events_reached` lists the events whose handlers were expanded, so a target missing from it was left unexpanded. An event not in the index returns empty `edges`, not an error. |
| `events-from-method` | `{ method_fqcn, dispatches, chains }`: what `dispatches-from` returns, plus one `events-following` result per dispatched event. An unknown method returns both empty. |
| `route-to-events` | `{ route, note, chain }`; `chain` is an `events-from-method` result and `note` is `null` when it resolved. A closure route returns the route with `chain: null` and a note. No matching verb and URI is an error. |
| `impact-of-change` | For a listener: `{ fqcn, change, kind, handles, would_orphan_events, dispatches, notes }`. For an event: `dispatchers`, `handlers` (`{ handler, handler_kind }`) and a `downstream` chain instead. An unknown class returns `kind: "unknown"`, `downstream: null` and a note. An unrecognised `change` is an error. |
| `find-orphans` | `{ orphan_events, idle_listeners }`: events nothing fires and nothing handles, and listeners that handle no event. An event fired only from an unresolved dispatch can look orphaned; cross-check with `find-unresolved-dispatches`. |
| `find-unresolved-dispatches` | `{ count, unresolved_dispatches }`; each is `{ file, line, expression, reason }`. The reasons are explained in [Why was my code missed](../guides/why-was-my-code-missed.md#a-dispatch-shows-up-as-unresolved). |
