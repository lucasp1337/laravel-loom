# Changelog

All notable changes to `laravel-loom` will be documented in this file. This project adheres to [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- **RouteScanner.** A new top-level `routes[]` section captures HTTP routes statically parsed (nikic/php-parser, no Laravel boot) from every `*.php` file under `routes/`. Recognised forms: `Route::<verb>('/uri', action)` for `get` / `post` / `put` / `patch` / `delete` / `options`; `Route::any(...)` (`method: "ANY"`); and `Route::match([...], '/uri', action)`, which emits one entry per listed verb. Action forms resolved into `controller_fqcn` / `controller_method`: tuple `[Ctrl::class, 'method']`, invokable (`Ctrl::class` or single-element `[Ctrl::class]` → `__invoke`), legacy string `'Ctrl@method'`, and closures (both controller fields `null`). The route name is captured from a chained `->name('...')`. Each entry carries `method` (uppercased verb), `uri` (enclosing group prefixes applied; leading slash, root `/`), `name` (group name prefix + leaf name, or `null`), `controller_fqcn` (or `null`), `controller_method` (or `null`), `middleware` (the resolved chain: enclosing-group middleware outermost-first followed by the route's own `->middleware(...)`, in source order, exact-duplicate names deduped; `[]` when none), `file` (relative to app root), and `line` (1-indexed registration line). Routes inside `Route::group(...)` inherit the group's context — both the array-config form `Route::group(['prefix' => 'admin', 'as' => 'admin.', 'controller' => C::class], fn)` and the fluent form `Route::prefix('admin')->name('admin.')->controller(C::class)->group(fn)` are read: the group `prefix` is prepended to the `uri` (nested groups concatenate, e.g. `/v2/users/{id}`); the group `as` / `name(...)` prefix is concatenated as-is with the leaf `->name(...)` (e.g. `admin.users.show`); a group `controller(C::class)` resolves a bare method-name string action to that controller without overriding an action that already names a class; and group `middleware` (fluent `Route::middleware([...])->group(...)` or array-config `['middleware' => [...]]`) is accumulated into the leaf route's `middleware` chain ahead of the route's own. Recognised middleware forms (on both route and group): single string, array, chained `->middleware('a')->middleware('b')`, variadic `->middleware('a', 'b')`, and `::class` references resolved to FQCN; arguments with parameters (`throttle:60,1`, `can:update,post`) are kept verbatim. `Route::resource('photos', PhotoController::class)` and `Route::apiResource(...)` are expanded into their constituent CRUD routes — one entry per generated action: a full `resource()` yields seven (`index`, `create`, `store`, `show`, `edit`, `update`, `destroy`), `apiResource()` yields the same set minus `create` / `edit` (five). Each generated entry carries the default name (`photos.index`, …), member parameter (Laravel's `Str::singular` of the resource name: `photos` → `{photo}`, `categories` → `{category}`), and the resource controller's matching action method; `update` is emitted as `PUT` (Laravel also accepts `PATCH` for it — the `PATCH` alias is not separately synthesized). Enclosing group prefix / name prefix / middleware propagate to all generated sub-routes, and `->only([...])` / `->except([...])` filter the action set. `stats.routes` is added. Schema changes: new `$defs/route`, new `routes` top-level array, `stats.routes` integer. Documented gaps (planned follow-up): middleware groups (e.g. `web`, `api`) are captured as-is, not expanded into their constituent classes (needs HTTP kernel config); middleware aliases are not resolved to class names; `withoutMiddleware(...)` subtraction is not applied; resource override forms `->names(...)` / `->parameters(...)` / `->scoped(...)` / `->shallow()` are not applied (default names and parameters always used); nested / dotted resource names (`photos.comments`) are treated flat, not specially expanded; batch `Route::resources([...])` / `apiResources([...])` array forms are not expanded; attribute routing (`#[Route]`) not handled; unresolvable actions (e.g. an action stored in a variable) emit null controller fields rather than guessing. Part of #8. See [docs/scanners/routes.md](docs/scanners/routes.md).

  Each route entry now also carries a `dispatches[]` cross-link (positioned last, after `line`): the events and jobs dispatched inside the route's controller method, reusing the shared `$defs/dispatch` reference shape (`{ target, kind (event|job), confidence, file, line }`) already used by `listeners[*].dispatches` / `jobs[*].dispatches`. A new `RouteDispatchAttributionPhase` cross-link phase attributes each dispatch site to a route by matching the site's enclosing class+method to the route's resolved `(controller_fqcn, controller_method)` — so an event can be traced back through its dispatching controller to the route that reaches it (the cross-section link #8 is fundamentally about). Closure routes, unresolved-controller routes (null controller fields), and controller methods that dispatch nothing carry `[]`; mailables / notifications are tracked through their own reverse-links, not here. Part of #8.

  Schema notes: a new top-level section is an additive, pre-1.0 minor change — `loom_version` bumps `0.2.0` → `0.3.0`.

- **`closure_listeners[*].dispatches` is now populated.** Any event or job dispatched inside a closure listener's body is attributed to that closure listener and appears in its `dispatches[]` array, using the same dispatch-object shape as `listeners[*].dispatches` — `{ target, kind (event|job), confidence (high|medium|low), file, line }`. Closure listeners have no class/method identity to key on, so attribution is **positional by source span**: a dispatch site is attributed to a closure listener when they share a file and the dispatch's line falls within `[line, end_line]` inclusive. To support this, each `closure_listeners[]` entry now carries a new **required** `end_line` field (the closure body's closing line; `line` remains the opening line). Only statically-resolved dispatches are captured — a dynamic/unresolvable target inside a closure goes into neither `dispatches[]` nor `unresolved_dispatches[]`. The reverse edge is intentionally absent: a dispatch made inside a closure appears in the closure's `dispatches[]` but the target's `dispatched_from[]` does not list the closure as a source (consistent with `events[*].handled_by` skipping closures — closures have no nameable identity). Nested closures: a dispatch inside a closure nested within a listener closure is attributed to every enclosing closure-listener span. Closes #16. See [docs/scanners/closure-listeners.md](docs/scanners/closure-listeners.md).

  Schema notes: the new required `end_line` field on `closure_listeners[]` is a major-class change, held under the pre-1.0 exemption — `loom_version` stays `0.2.0`, not bumped. This release also corrects a latent schema defect: `closure_listeners[*].dispatches` items are dispatch **objects** (previously mis-declared as strings, but always empty so never exercised) and now reference the shared `$defs/dispatch`.

- **`name` and `even_in_maintenance_mode` captured on schedule entries.** Each `scheduled[]` entry now carries `name` (the string passed to `->name('...')`, or `null` when no name is set) and `even_in_maintenance_mode` (`true` when `->evenInMaintenanceMode()` is chained, otherwise `false`). Closes group 1 of #28. See [docs/scanners/schedule.md](docs/scanners/schedule.md).

  Schema notes: the new required `name` and `even_in_maintenance_mode` fields on `scheduled[]` are a major-class change, held under the pre-1.0 exemption — `loom_version` stays `0.2.0`, not bumped.

- **Argument capture on schedule helpers.** Each `scheduled[]` entry now surfaces three previously-discarded pieces of data. `arguments` (array of strings, command kind only, otherwise `[]`) records the literal parameters array passed to `->command(Class::class, [...])`: plain items render as the stringified value (`['--force']` → `["--force"]`), keyed items as `"key=value"` (`['user' => 1]` → `["user=1"]`), booleans as `"true"`/`"false"`; non-literal items are skipped. `queue` and `connection` (string or `null`, job kind only) record the 2nd/3rd arguments of `->job($job, $queue, $connection)`. `without_overlapping_expires_at` (integer or `null`) records the expiry minutes from `->withoutOverlapping($minutes)` — `null` when called with no literal argument (the framework's 1440 default is intentionally not fabricated). The boolean `without_overlapping` is unchanged. Closes group 2 of #28. See [docs/scanners/schedule.md](docs/scanners/schedule.md).

- **Sub-minute scheduling frequencies recognised via a structured `frequency` field.** Laravel's `everySecond` / `everyTwoSeconds` / `everyFiveSeconds` / `everyTenSeconds` / `everyFifteenSeconds` / `everyTwentySeconds` / `everyThirtySeconds` helpers cannot be expressed as a five-field cron, so they previously emitted `cron: null` with no further detail. Each `scheduled[]` entry now carries a `frequency` field — `null` for ordinary entries, or `{ "unit": "seconds", "every": <N> }` for a sub-minute schedule (e.g. `->everyFifteenSeconds()` → `{ "unit": "seconds", "every": 15 }`, with `cron` staying `null`). The `unit` is backed by a new `FrequencyUnit` enum (currently only `seconds`, extensible later). A cron-based helper and a sub-minute helper are mutually exclusive and resolve last-wins in both directions (`->everyFifteenSeconds()->daily()` → cron set, `frequency` null; `->daily()->everyFifteenSeconds()` → `cron` null, `frequency` set). Closes group 3 of #28. Rationale recorded in [docs/adr/0004-sub-minute-frequencies.md](docs/adr/0004-sub-minute-frequencies.md). See [docs/scanners/schedule.md](docs/scanners/schedule.md).

- **Scheduling groups recognised.** Laravel 11's `Schedule::daily()->onOneServer()->group(function () { ... })` shares the outer chain's frequency and modifiers across every task declared inside the group closure. These inner tasks were previously emitted without the inherited attributes (or, for the wrapper, ignored entirely). Each task inside a `->group(Closure)` block now emits as an ordinary `scheduled[]` entry whose attributes are the group's chain merged with the task's own — the task's own modifiers win on conflict (an inner `->weekly()` overrides the group's `daily`). Both the facade form (`Schedule::...->group(...)`) and the kernel variable form (`$schedule->...->group(...)`) are recognised, and nested groups concatenate (outer attributes apply to inner). No schema change — inner tasks carry no special marker. Closes group 4 of #28. See [docs/scanners/schedule.md](docs/scanners/schedule.md).

  Schema notes: the new required `arguments`, `queue`, `connection`, `without_overlapping_expires_at`, and `frequency` fields on `scheduled[]` are a major-class change, held under the pre-1.0 exemption — `loom_version` stays `0.3.0` (already bumped this cycle by the RouteScanner work), not bumped further. Lifecycle hooks (`before`/`after`/`onSuccess`/`onFailure`/`ping*`/output handlers) and an app-default scheduling timezone (`scheduleTimezone()`) remain deliberately uncaptured — group 5 of #28, deferred until a consumer asks.

- **Channel-filter argument captured as `channels` on notification dispatch sites.** The `Notification::send($users, $notification, $channels)` / `Notification::sendNow($users, $notification, $channels)` facade forms accept an optional third argument — an array of channels that restricts that dispatch to a specific channel set, overriding the notification's own `via()` declaration. Each `notifications[*].notified_from` entry now carries an optional `channels` array recording this filter when it's a literal array of string channel names and/or `Class::class` channel constants. Values mirror the `notifications[*].channels` shape: lowercased channel names (`"mail"`, `"database"`) and/or custom channel-class FQCNs (`"App\\Channels\\SmsChannel"`). The key is omitted entirely when the argument is absent, empty, or non-literal (e.g. a `$variable` or `$user->preferredChannels()`) — existing consumers see no shape change, so this is a non-breaking additive (minor) change. Captured only on the `Notification::send`/`sendNow` facade form; the `->notify(...)` method form has no channel-filter argument. Gaps: dynamic channel filters (`$user->preferredChannels()` etc.) are not captured, and `Notification::route(...)->notify(...)` chains carry recipient routing, not a channel filter, so no `channels` is emitted there. Closes #33. See [docs/scanners/notifications.md](docs/scanners/notifications.md) and [docs/scanners/dispatches.md](docs/scanners/dispatches.md).

- **Dispatch-time chain modifiers captured as `overrides`.** Each dispatch-site entry (`events[*].dispatched_from`, `jobs[*].dispatched_from`, `mailables[*].sent_from`, `notifications[*].notified_from`) now carries an optional `overrides` object recording statically-resolvable fluent modifiers applied at the dispatch site. Keys (all optional, only present keys emitted): `locale`, `mailer`, `connection`, `queue` (strings), `delay` (integer seconds), `after_commit` (boolean, only ever `true`). Source mapping: `->locale('es')`, `->mailer('ses')`, `->onConnection('redis')`, `->onQueue('high')`, `->delay(60)`, `->afterCommit()`. Both the inner argument-instance chain (`dispatch((new ProcessOrder)->onQueue('high'))`, `$user->notify((new InvoicePaid)->onQueue('emails'))`, `Mail::to($u)->send((new OrderShipped)->locale('fr'))`) and the outer PendingDispatch chain on jobs and events (`ProcessOrder::dispatch($o)->onQueue('high')->onConnection('redis')`, `dispatch(new ProcessOrder)->afterCommit()`), plus the Mail facade receiver chain (`Mail::to($u)->locale('fr')->mailer('ses')->send($m)`), are read. The `overrides` key is omitted entirely on sites with no static modifier — existing consumers see no shape change, so this is a non-breaking additive (minor) change. Gaps: `->delay()` with a non-integer-literal argument (`->delay(now()->addMinutes(5))`, `->delay($seconds)`) is not captured; modifiers set on a separate statement before dispatch are out of static reach; the Notification facade-receiver form (`Notification::locale('es')->send($users, $n)`) is not detected (notifications read inner-argument chains only). Closes #32. See [docs/scanners/dispatches.md](docs/scanners/dispatches.md), [docs/scanners/jobs.md](docs/scanners/jobs.md), [docs/scanners/mailables.md](docs/scanners/mailables.md), and [docs/scanners/notifications.md](docs/scanners/notifications.md).

### Changed

- **Dispatch targets wrapped in a fluent chain now resolve to their FQCN.** `AstHelpers::resolveStaticClass()` unwraps a leading fluent `MethodCall` chain before resolving the dispatched class, so a `new X` / `X::class` receiver buried under chain modifiers is statically resolved instead of being dropped into `unresolved_dispatches[]` with reason `dynamic_class_name`. Newly resolved forms include `dispatch((new ProcessOrder())->delay(60))`, `ProcessOrder::dispatch()->onQueue('high')`, `Mail::to($user)->send((new OrderShipped)->locale('fr'))`, `Mail::send((new OrderShipped)->onConnection('redis'))`, `$user->notify((new InvoicePaid)->locale('es'))`, and `Notification::send($users, (new InvoicePaid)->onQueue('emails'))`. Each lands in the appropriate reverse-reference array (`jobs[*].dispatched_from`, `events[*].dispatched_from`, `mailables[*].sent_from`, `notifications[*].notified_from`) instead of `unresolved_dispatches[]`. The chain modifier *values* themselves (`->delay(60)`, `->onQueue('high')`, `->locale('fr')`) are still not captured into `queue_config` or any other field — only the target FQCN is resolved through the chain; modifier capture is tracked separately under #32. Variable receivers (`$instance->locale('es')` where `$instance` is a variable) remain unresolved; only `new X` and `X::class` receivers resolve through the chain. Closes #31. See [docs/scanners/dispatches.md](docs/scanners/dispatches.md), [docs/scanners/jobs.md](docs/scanners/jobs.md), [docs/scanners/mailables.md](docs/scanners/mailables.md), and [docs/scanners/notifications.md](docs/scanners/notifications.md).

- **Transitive `ShouldQueue` detection for jobs and listeners.** `JobsScanner` and `ListenerScanner` now consult the `ClassHierarchyResolver` when computing `queued`. A job or listener reports `queued: true` whenever any class in its `extends` chain (or the class itself) declares `implements Illuminate\Contracts\Queue\ShouldQueue`, as long as the relevant parent class is indexed under `app/`. The visitor-level check on the direct `implements` clause is preserved for unit tests, but the scanner-emitted answer is the transitive one. Vendor-class parents remain opaque to the resolver and won't surface as `queued: true`. Documented gap closed: indirect `ShouldQueue` via `app/`-resident parent class (issue #14). See [docs/scanners/jobs.md](docs/scanners/jobs.md) and [docs/scanners/listeners.md](docs/scanners/listeners.md).

### Added

- **MailableScanner.** A new top-level `mailables[]` section captures mailable classes discovered via two paths: a recursive filesystem walk of `app/Mail/`, and dispatch-site seeding (any class targeted by `Mail::send(new X)`, `Mail::send(X::class)`, `Mail::queue(...)`, `Mail::later($delay, ...)`, or the chained forms `Mail::to(...)->send(new X)` / `->queue(new X)` / `->later($delay, new X)` — including chains through `->cc(...)`, `->bcc(...)`, `->locale(...)`, `->mailer(...)` — is located via PSR-4 and parsed, so mailables in DDD layouts like `app/Domain/Billing/Mail/` get picked up). Entries are deduped by FQCN. Abstract classes, interfaces, traits, and anonymous classes are skipped. Each entry carries `queued` (true whenever the class transitively implements `Illuminate\Contracts\Queue\ShouldQueue` via the `ClassHierarchyResolver`) and `queue_config` (the same six-field `$defs/queueConfig` block as jobs: `connection`, `queue`, `delay`, `tries`, `timeout`, `backoff`, `null` when not declared as a scalar class property). `queue_config` is `null` when `queued` is `false`. The cross-link pass populates `mailables[*].sent_from` from dispatch sites with finalized `kind === 'mailable'` whose `target` matches a mailable FQCN. `stats.mailables` is added. Schema changes: new `$defs/mailable`, new `mailables` top-level array, `stats.mailables` integer, new `provisionalKind: 'mailable'` value emitted by `DispatchSiteVisitor`. Documented gaps: `Mail::raw($body, $closure)` is skipped (no FQCN to index); `Mail::send($variable)` flows to `unresolved_dispatches[]` per the standard contract but the target class doesn't enter `mailables[]`; `ShouldQueue` inherited through vendor parents (classes outside `app/`) is opaque; method-form queue configs (`backoff()`, `retryUntil()`) are not parsed; dispatch-site chaining (`->onQueue(...)`, `->onConnection(...)`, `->delay(...)`) is not folded into the entry; non-scalar property initializers leave the field `null`. See [docs/scanners/mailables.md](docs/scanners/mailables.md) and [ADR 0003](docs/adr/0003-mailables-notifications.md).

- **NotificationScanner.** A new top-level `notifications[]` section captures notification classes discovered via two paths: a recursive filesystem walk of `app/Notifications/`, and dispatch-site seeding from `$any->notify(new Y)` / `$any->notify(Y::class)`, `$any->notifyNow(new Y)`, `Notification::send($recipients, new Y)`, `Notification::sendNow(...)`, and `Notification::route(...)->notify(new Y)` chains (including longer route chains). Receiver-class inspection is intentionally out of scope: matching the method name is sufficient given `Notifiable` is the canonical receiver. Entries are deduped by FQCN. Abstract classes, interfaces, traits, and anonymous classes are skipped. Each entry carries `queued`, `queue_config` (identical shape to mailables and jobs), `channels[]` extracted from a statically resolvable `via()` method body, `channels_dynamic` (a boolean signalling whether `via()` exists but is not statically resolvable), and a cross-link-populated `notified_from`. Channel extraction recognises a single `return [...];` body whose items are literal strings (stored lowercased) or `Class::class` constants (stored as FQCN). Channels are emitted in source order — Laravel dispatches over them in that order, and source order preserves user intent. `channels_dynamic` is `true` only when `via()` exists *and* its body is not the recognised shape (conditional return, property/method access, variable item, keyed entry); when no `via()` method is declared at all, `channels` is `[]` and `channels_dynamic` is `false` — an intentional zero rather than an unknown. The cross-link pass populates `notifications[*].notified_from` from dispatch sites with finalized `kind === 'notification'` whose `target` matches a notification FQCN. `stats.notifications` is added. Schema changes: new `$defs/notification`, new `notifications` top-level array, `stats.notifications` integer, new `provisionalKind: 'notification'` value emitted by `DispatchSiteVisitor`. Documented gaps: conditional `via()` bodies produce `channels: []` with `channels_dynamic: true` (no union over branches); `via()` inherited from a parent class or trait is invisible (method-level hierarchy resolution is reserved per ADR 0001 §3) and yields `channels_dynamic: false`; `shouldSend()` runtime gating is ignored; receiver-class blindness (`$user->notify(...)` doesn't tell Loom which model receives the notification); `$user->notify($variable)` flows to `unresolved_dispatches[]` but the target class doesn't enter `notifications[]`; `ShouldQueue` inherited through vendor parents is opaque; method-form queue configs and dispatch-site chaining are not parsed. See [docs/scanners/notifications.md](docs/scanners/notifications.md) and [ADR 0003](docs/adr/0003-mailables-notifications.md). Closes #6.

- **`ClassHierarchyResolver` support service.** Internal cross-file resolver for `extends` / `implements` / `use Trait` relationships, backed by a new `ClassDeclarationVisitor`. Lives at `src/Support/ClassHierarchyResolver.php`; lazy-indexes `app/` once per `IndexBuilder::build()` call and memoises per-FQCN queries. Exposes `extendsChain()`, `implementsAll()`, `traitsAll()`, `implementsInterface()`, `isSubclassOf()`, and `knows()`. External classes are treated as opaque leaves. Consumed by `JobsScanner` and `ListenerScanner` for transitive `ShouldQueue` detection (see the related "Changed" entry); other scanners may adopt it as the depth-fix backlog lands. Contract at [docs/support/class-hierarchy.md](docs/support/class-hierarchy.md); rationale in [ADR 0001](docs/adr/0001-class-hierarchy-resolver.md). Closes #13.

- **ScheduleScanner.** A new top-level `scheduled[]` section captures entries declared in Laravel's task scheduler. Three discovery paths, merged on `(file, line, kind, target)`: a class declaration at `app/Console/Kernel.php` carrying a `schedule(Schedule $schedule)` method; the `->withSchedule(function (Schedule $schedule) { ... })` closure on the `Application::configure(...)` chain in `bootstrap/app.php`; and any `Schedule::call(...)`, `Schedule::command(...)`, `Schedule::job(...)`, or `Schedule::exec(...)` chain anywhere under `app/` where `Schedule` resolves to `Illuminate\Support\Facades\Schedule`. Each entry carries `kind` (`command` / `job` / `closure` / `exec`), `target` (signature string or FQCN, or `"FQCN::method"` for tuple- and `Class@method`-callable closures, or `null` for inline closures), `cron` (canonical five-field expression for every recognised frequency helper, with `cron(string)` passed through verbatim; `null` when no recognised helper appears or its argument is non-static), `timezone`, the `without_overlapping` / `on_one_server` / `run_in_background` flags, and `constraints[]` (opaque sorted labels for day-of-week, `between` / `unlessBetween`, `when` / `skip`, and `environments`). When multiple frequency helpers chain together, last wins (mirrors Laravel's runtime). `stats.scheduled` is added. Cross-link is one-directional: `scheduled[*].target` with `kind: "job"` carries a job FQCN that consumers join against `jobs[*].fqcn` client-side; no `jobs[*].scheduled` back-pointer is added. Schema additions: new `scheduled` top-level array, new `$defs/scheduleEntry`, `stats.scheduled`. Documented gaps: L10-only apps (kernel form still works incidentally but isn't a supported target); runtime macros (`Schedule::macro(...)`) leave `cron: null`; helpers outside the recognised table yield `cron: null`; non-static frequency arguments (`->dailyAt($time)`) yield `cron: null`; `->ping*()` callbacks are not captured; `Bus::chain([...])` / `Bus::batch([...])` inside a closure schedule are not captured (the schedule entry is, its inner job composition isn't); job targets whose FQCN lives outside `app/` resolve but have no matching `jobs[]` row; schedules registered outside the three discovery surfaces (e.g. via reflection in a deferred provider, or in `routes/console.php`) are invisible. Closes #7. See [docs/scanners/schedule.md](docs/scanners/schedule.md) and [ADR 0002](docs/adr/0002-schedule-scanner.md).

- **JobsScanner.** A new top-level `jobs[]` section captures job classes discovered via two paths: a recursive filesystem walk of `app/Jobs/`, and dispatch-site seeding (any class targeted by `dispatch(new X)`, `Bus::dispatch(new X)`, or `X::dispatch()` is located via PSR-4 and parsed, so jobs in DDD layouts like `app/Domain/Billing/Jobs/` are picked up). Entries are deduped by FQCN. Abstract classes, interfaces, traits, and anonymous classes are skipped. Each entry carries `queued` (true whenever the class transitively implements `Illuminate\Contracts\Queue\ShouldQueue` — see the related "Changed" entry on transitive detection) and `queue_config`. `queue_config` is `null` when `queued` is `false`; otherwise it's an object with all six keys present — `connection`, `queue`, `delay`, `tries`, `timeout`, `backoff` — each being the scalar literal declared as a class property or `null` when not declared (in which case the framework default applies at runtime). The cross-link pass populates `jobs[*].dispatched_from` from dispatch sites with finalized `kind === 'job'`, and `jobs[*].dispatches` from dispatch sites inside the job's `handle()` method. `stats.jobs` is added. Schema changes: new `$defs/job`, new `$defs/queueConfig`, and the dispatch-site shape previously inlined under `events[*].dispatched_from` is promoted to a shared `$defs/dispatchSite` (same shape, single source of truth) now referenced by both `events[*].dispatched_from` and `jobs[*].dispatched_from`. Documented gaps: `ShouldQueue` inherited through vendor parents (classes outside `app/`) is not detected; dispatches in helper methods called from `handle()` are not attributed; `Bus::chain([...])` and `Bus::batch([...])` are not captured by DispatchScanner; method-form configs (`backoff()`, `retryUntil()`) are not parsed; dispatch-site chaining (`->onQueue(...)`, `->onConnection(...)`, `->delay(...)`) is not parsed; non-scalar property initializers (`config('queue.default')` etc.) leave the field `null`; `ShouldBeUnique`, `ShouldBeEncrypted`, `Batchable`, and `InteractsWithQueue` flags are not surfaced. See [docs/scanners/jobs.md](docs/scanners/jobs.md).

## [0.2.0](https://github.com/lucasp1337/laravel-loom/compare/v0.1.0...v0.2.0) - 2026-05-17

### Changed

- **BREAKING — `listeners[*].handles` shape.** The array now holds `{event, method}` objects instead of bare event-FQCN strings. Both fields are always present; `method` defaults to `"handle"` for registrations that didn't name one (auto-discovery, bare `Listener::class` in `$listen`, bare `Listener::class` in `Event::listen()`). Entries are deduped by the `(event, method)` tuple and sorted by `event` then `method`.

  Migration: consumers reading `listener['handles']` previously got `["App\\Events\\OrderPlaced"]`; they now get `[{"event": "App\\Events\\OrderPlaced", "method": "handle"}]`. Extract the legacy shape with `array_map(fn ($h) => $h['event'], $listener['handles'])`.

- **BREAKING — `events[*].handled_by` shape.** The array now holds `{listener, method}` objects instead of bare listener-FQCN strings. Sorted by `listener` ascending then `method` ascending.

  Migration: consumers reading `event['handled_by']` previously got `["App\\Listeners\\SendOrderConfirmation"]`; they now get `[{"listener": "App\\Listeners\\SendOrderConfirmation", "method": "handle"}]`. Extract the legacy shape with `array_map(fn ($h) => $h['listener'], $event['handled_by'])`.

- `LOOM_VERSION` bumped to `0.2.0` to reflect the breaking schema changes.

### Added

- **Closure listener discovery.** A new top-level `closure_listeners[]` section captures closure and arrow-function registrations that `listeners[]` can't represent (no FQCN). Three discovery paths: closure values inside the `$listen` array on `EventServiceProvider` (`registration: "listen_array"`), closures as the second argument to `Event::listen()` anywhere under `app/` (`registration: "event_listen_call"`), and closures in a subscriber's `subscribe()` return-array (`registration: "subscriber"`). Both `fn ($e) => …` and long-form `function ($e) { … }` are detected. The `event` field holds the FQCN for `::class` registrations and the raw string for string-keyed registrations; `file`/`line` point to the closure node. The section is additive — existing consumers reading `listeners[]` see no shape change. `queued` is always `false` and `dispatches` is always `[]` in this release; both are reserved fields. `events[*].handled_by` does not link back to closures (their shape lacks an FQCN + method); filter `closure_listeners[]` by `event` instead. See [docs/scanners/closure-listeners.md](docs/scanners/closure-listeners.md).

- **Multi-handler listener support.** A single listener class registered against different events under different methods is now represented faithfully. Tuple-form registrations preserved across all four discovery paths:
  - `$listen` array: `EventClass::class => [[Listener::class, 'handleFoo']]` records `method: "handleFoo"`.
  - `Event::listen(EventClass::class, [Listener::class, 'handleFoo'])` records `method: "handleFoo"`.
  - Subscriber return-array tuple values `[Event::class => [self::class, 'handleFoo']]` and `[Event::class => [Subscriber::class, 'handleFoo']]` record `method: "handleFoo"`.
  - Bare `Listener::class` forms (in `$listen`, in `Event::listen()`) and auto-discovery default to `method: "handle"`.

  A listener can carry multiple `handles[]` entries for the same event under different methods; the dedupe key is the full `(event, method)` tuple.

- **ListenerScanner — subscriber discovery.** Detects subscriber classes registered via `$subscribe = [Subscriber::class, …]` on `EventServiceProvider` (or any class extending it) and via `Event::subscribe(Subscriber::class)` calls. The subscriber's own `subscribe()` method is parsed for return-array form (`return [Event::class => 'method', …]`), and the resulting events populate `handles[]`. Subscribers are emitted with `registration: "subscriber"` — a new highest-precedence source above `listen_array`.

- **ListenerScanner — imperative `subscribe()` body support.** The subscriber visitor now also walks the `subscribe()` method body in addition to its return-array, parsing `$events->listen(...)` calls against the dispatcher parameter. The dispatcher is identified by parameter position (any name, any type-hint). Control-flow statements (`if`, `foreach`, `try/catch`) are descended; nested closures and other method bodies are not. Routing: `[self::class | static::class | OwnFqcn::class, 'method']` and bare-string callables `'method'` contribute to the subscriber's own `handles[]`; `[OtherClass::class, 'method']` registers `OtherClass` as a regular `listeners[]` entry; closures and arrow functions flow into `closure_listeners[]`. All three forms are stamped `registration: "subscriber"`. A single subscriber can mix the return-array and imperative forms. **Behavior change:** when an imperative `$events->listen(...)` registers a *foreign* listener (one not declared on the subscriber's own class), that listener's `registration` is upgraded to `subscriber` — the highest-precedence source. Previously such foreign listeners were either invisible (the body wasn't parsed) or would carry their lower-precedence source. The schema is unchanged; the precedence rule (`subscriber > listen_array > event_listen_call > auto_discovered`) is unchanged. Out of scope and documented as gaps: nested `$events->subscribe(...)` calls inside `subscribe()`, registrations hidden inside nested closures or chained iterator callbacks (`collect()->each(fn () => $events->listen(...))`), and `listen(...)` calls on receivers other than the dispatcher parameter (`$this->dispatcher->listen(...)`).

### Fixed

- **Cross-link Phase 3 dispatch attribution for non-`handle` listener methods.** Previously, the listener-dispatch join keyed on the literal method name `handle`, so dispatches emitted from `handleOrderPlaced()` / `handleRefund()` / any custom handler method were silently dropped from `listeners[*].dispatches`. The join now matches when the dispatch's enclosing method is in the listener's `handles[*].method` set, so dispatches from custom handler methods are attributed to the listener.

### Added

- **Four static scanners** covering the primitives of Laravel's event-driven architecture:
  - `EventScanner` — event classes from `app/Events/` plus any class dispatched via `event()`, `Event::dispatch()`, or `X::dispatch()`.
  - `ListenerScanner` — listeners registered through the `$listen` array on `EventServiceProvider`, Laravel 11+ auto-discovery via typed `handle()` parameters, and `Event::listen()` calls anywhere under `app/` (DDD-style providers outside `app/Providers/` are supported). Dedupe precedence: `listen_array > event_listen_call > auto_discovered`.
  - `ObserverScanner` — observers registered via `Model::observe()` (including `static::observe(...)` in `booted()`), the `#[ObservedBy]` attribute, and `Event::listen('eloquent.*', …)` listener strings. Emits both `observers[]` and synthesized `model_events[]`. Dedupe precedence on same `(observer, model)` pair: `attribute > observe_call`.
  - `DispatchScanner` — one-level dispatch-site scan of every class method body. Recognises `event()`, `Event::dispatch()`, `X::dispatch()`, `dispatch()`, and `Bus::dispatch()`. Surfaces unresolvable dispatches as `unresolved_dispatches[]` entries with one of four reason codes.
